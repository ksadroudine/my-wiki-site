## Summary

Why private (internal) APIs typically create more business value than public ones, despite getting less attention. Covers the API value chain (business-asset owner, provider, developer, app, end user) that determines whether an API program succeeds, and the private/public/monetization choices that shape API strategy.

## Highlights

- An API is fundamentally a contract: the provider commits to what functionality will be offered, when it may change, and under what constraints, which lets developers build against it with confidence — and any change to that contract has a potentially large ripple effect on every app already built on top of it. <span class="src">APIs</span>
- Private and public are best understood as describing the formality of the business arrangement with the API's consumers, not the technical content of the API itself; a company frequently starts with a private API and later opens some or all of it publicly, or vice versa, once it discovers where the real business value actually lies. <span class="src">APIs</span>
- Private APIs are argued to create more business value than public ones by an order of magnitude in most companies, because the biggest, most visible public APIs (Twitter's, Google's) are the exception rather than the rule — most companies' greatest returns come from using APIs internally to accelerate their own mobile, web, and partner-facing development. <span class="src">APIs</span>

## Concept

APIs (Jacobson, Brail, and Woods) argues that an application programming interface is best understood, at its core, as a contract between a provider and the developers who build against it: the provider commits to specific functionality, to advance notice of breaking changes, and often to explicit technical and business constraints (rate limits, usage terms), and this contract is what gives developers the confidence to build real, dependent applications on top of the API — which is also why altering that contract carries a potentially large ripple effect across every application already relying on it. The source draws a sharper distinction between private and public APIs than is common in popular discussion of the topic, arguing that "private" and "public" describe only the formality of the business arrangement governing who may use the API and under what terms — not any technical property of the API itself, and not whether its ultimate content reaches end users. Companies frequently move in either direction over time: starting with a private API and later opening some or all of it to the public once external demand becomes clear, or launching publicly and later discovering that the greater realized value actually comes from internal, private use. <span class="src">APIs</span>

The book's most counterintuitive and central claim is that private APIs typically create substantially more business value than public ones — described as an order of magnitude more in most companies — precisely because the handful of highly visible public API success stories (Twitter, Google, Facebook) are the exception rather than the representative case; for the overwhelming majority of companies, an API's greatest realized value comes from using it internally to accelerate the company's own mobile, web, and partner-facing development, letting internal and partner teams build new applications in weeks rather than the months or years a traditional, siloed enterprise IT process would require. This argument reframes what "success" should even mean for most API programs: rather than measuring an API's value by external developer adoption or public traffic, the book directs attention to internal ROI — how much faster and cheaper internal development becomes once teams can subscribe to clean, consistent, self-service interfaces instead of navigating bespoke point-to-point integrations with each internal system. <span class="src">APIs</span>

An API program's success or failure is analyzed through a five-link value chain that must hold together end to end: the owner of the underlying business assets (data, content, or services being exposed), the API provider who designs and operates the API itself (frequently, but not always, the same party as the asset owner), the developers who consume the API to build applications, the applications those developers actually produce, and the end users who ultimately use those applications and generate the value the whole chain exists to capture. The book's diagnosis of failed API strategies is almost always a weak link somewhere in this chain rather than a purely technical shortcoming — most commonly, a program launched without buy-in from stakeholders across the business (legal, product, marketing, and the actual owners of the underlying business assets), leaving the resulting API technically sound but commercially disconnected from what the business actually needs it to accomplish. On monetization specifically, the book catalogs the recurring commercial models an API program can adopt: Free (no charge at all, valuable mainly for the reach, goodwill, or "cool factor" it generates rather than direct revenue), Developer Pays (which itself has several variants — tiered pricing, pay-as-you-go, per-unit consumption, or freemium with paid upgrades), Developer Gets Paid (revenue-share arrangements such as advertising splits, or affiliate models like cost-per-action or cost-per-click), and Indirect (where the API's value comes from driving some other core business metric — a retailer's store-locator API driving physical store visits, for instance, rather than generating direct API revenue). Among these, the book identifies "internal ROI" — value realized purely from faster, cheaper internal development enabled by the API, independent of any external monetization model — as the single most consequential category in practice, precisely because it is the one most likely to be overlooked by teams focused on public-facing monetization strategy. <span class="src">APIs</span>

Before any technology decisions are made, the book insists an API strategy must answer a specific set of questions: who is the intended audience (internal staff, contractual partners, or the open public), what business assets will actually be exposed and to whom, and — critically — what will actually motivate developers to build applications using the API, since an API with no compelling developer motivation will attract no real usage regardless of its technical quality. The book also stresses the organizational precondition for success: an API program needs an identifiable internal business sponsor, since programs lacking one are reported to consistently struggle to secure funding and organizational attention regardless of the API's underlying technical merit. Finally, behind nearly every successful API program studied in the source — public or purely internal — is a developer evangelist: someone technically credible enough to build real applications with the API themselves, who actively participates in the relevant developer communities (internal forums for a private API, or public venues like GitHub and Stack Overflow for a public one) and provides fast, real-time support and feedback, rather than treating API publication as a one-time technical release. <span class="src">APIs</span>
